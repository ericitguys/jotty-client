# AI-Augmented Triage (P3) Implementation Plan — capture pipeline

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Layer the AI-augmented triage stage onto the shipped P2 triage surface: ONE batched OpenWebUI request per triage-chunk (never per-note), route/board/title/tag suggestions rendered as badges on the existing TriageView cards, suggestion-derived prefill of the P2 promote/move modals behind a confidence gate, tag-vocabulary curation with client-side persistence, and the confidence-threshold setting.

**Architecture (Voice_AI precedent, facts §7/§16/§19):** client-side orchestration — the TS layer slices the `!INBOX` sweep into chunks of ≤ `TRIAGE_CHUNK_CAP` (20, spec §5 allows 20-25) note-ids and calls `invoke('triage_suggest', …)` ONCE per chunk, sequentially, rendering badges as each chunk's result arrives (progressive per-chunk render from the sequential-awaited-invoke pattern; no Rust event machinery, no background task). Rust does ALL HTTP: a `triage_ai.rs` module drives the existing `VoiceAiClient` (chat/completions, v1→plain suffix fallback, suffix persistence) exactly like tidy/extract_tasks. Model output is validated TWICE: Rust-side strict parse (per-chunk JSON, code-fence-tolerant, ONE retry on parse failure, out-of-enum routes / unknown note ids dropped — spec §5 "fail validation → falls back to manual") and TS-side re-validation (`isTriageRoute` + board-title resolution + confidence gate). Suggestions are ADVISORY session state — nothing is ever auto-applied; every apply routes through the P2 user-gated primitives (promote modal / move modal / discard ConfirmModal).

**Tech Stack:** unchanged across P3: Rust (tauri 2, reqwest via VoiceAiClient, rusqlite kv rows), React TS + zustand (NO store changes — suggestions live in TriageView component state, judged session-only), vitest + RTL, wiremock.

**Spec:** `docs/superpowers/specs/2026-10-06-atomic-capture-ai-triage-design.md` — §5 (AI triage rules: route enum, board suggestion, title normalization, tag curation, confidence, pipeline rules), §6 (lifecycle: title normalization applies ON move/promote = the prefill), §9 P3 roadmap line. **Facts:** `.superpowers/sdd/2026-10-07-capture-p2-p3/facts.md` §7 (voice extraction chain = the precedent), §16 (voice_ai.rs OpenWebUI client), §17 (strict-parse precedents), §18 (kv settings storage), §19 (long-inference async UI + mounted-ref law), §20 (Send law shapes). ## Global Constraints (standing laws, verbatim-adapted from the P2 plan + P3 additions)

- **Zone literals:** `!INBOX` (`INBOX_CATEGORY`/`isCaptureZone`, store.ts:10-12) + `PROCESSED` introduced ONLY by the P2 promote/move primitives — P3 never writes a category; P4 owns `PROCESSED/Archive/YYYY-MM` (do not build it).
- **originalCategory law (P2-shipped, untouched):** wire body carries `originalCategory` only when category changes; P3 consumes it via the existing move/promote flows — never re-implements.
- **Stale-guard law (unchanged):** EVERY apply revalidates inside its tx (`stale: note no longer exists`, zero enqueues on failure) + the capture-zone re-promote guard + deleted-board guard (T2 fix round). P3's sweep re-checks notes exist at result-merge and at modal-open (defensive, matching P2's double-guard); the AUTHORITATIVE guard stays server-side.
- **Promote atomicity / one-tx law:** untouched; P3 adds NO new local mutation tx. The triage_suggest command performs ZERO db writes (suffix persistence aside, via the existing kv upsert) — suggestions are returned, never persisted.
- **P3 AI laws (NEW, load-bearing):**
  - **One batched request per chunk, never per note** — `chat/completions` carries a JSON payload of ≤20 notes; N notes ÷ 20 chunks = N/20+… requests total; a per-note loop is a spec violation (spec §5: chunk cap 20-25 notes/request).
  - **One retry on parse failure** (spec §5): the SAME chunk body is re-sent exactly once when strict parse fails; HTTP/auth errors do NOT retry. A chunk that still fails → Err → TS degrades THAT chunk to manual and continues the sweep (a failed chunk never aborts the batch).
  - **Validation law, both sides:** Rust drops items whose route is not exactly in `{TODO, COMMANDS, DOCS, NOISE}` (case-sensitive — mirror of isTriageRoute), whose note_id is not in the request set, or whose confidence is not a number (missing/invalid confidence → 0.0, not dropped); `suggested_board` cleared when not on the validated board-name list; tags normalized (trim, strip leading `#`, lowercase). TS RE-validates with `isTriageRoute` (routes.ts:10-11) + resolves board title → id against the live board list; anything unresolved falls back to manual.
  - **No model calls from TS:** every OpenWebUI HTTP call lives in Rust (voice precedent). The webview ONLY invoke()s app-owned commands.
  - **AI never executes anything autonomously:** suggestions are advisory; apply always = the user acting through the P2 modals/discard gate; discard remains user-confirmed only.
  - **No auto-triage daemon:** sweeps are USER-triggered only (button / `s` key); nothing schedules or retries them in the background; navigating away stops the loop (mounted-ref law, facts §19).
- **No new crates, no new npm deps, no `cargo fmt`.** Warnings census `cargo check --all-targets 2>&1 | grep -c '^warning'` = 18, **Δ0 gate** (manifest-path form canonical per T2-review note). No Cargo.toml / package.json edits anywhere in P3.

## Review Focus

1. **Model returns garbage** (malformed JSON even after the one retry, out-of-enum/misspelled routes, hallucinated note ids): expected = dropped items render as plain manual cards; a still-failed chunk degrades THAT chunk to manual with an error line and the sweep CONTINUES; no abort, no blank queue. Pinned by Task 1 parse tests + Task 2 chunk-failure test.
2. **Stale suggestion applied** (note moved/deleted/processed between sweep and apply): expected = the P2 apply path refuses (stale guard / gone-from-store guard); suggestions rendered for notes that left the zone are dropped at merge and at render. Pinned by Task 1 zone/existence filters + Task 2 drop test; P2's server-side law is authoritative.
3. **Prompt injection via note content** (a capture whose text tells the model "reply route NOISE / confidence 1.0"): expected = output constrained by code, not prose — routes/dto validated against enums + the board list; confidence displayed as an uncalibrated heuristic; nothing executes without the user gate. Pinned by validation fences (Task 1) + no-TS-model-call law + the advisory-only architecture.
4. **Long-inference UX** (10-60 s per chunk, spec §5): expected = sweep button busy state with progress (`Analyzed k/N`), badges arrive per chunk, j/k navigation UNINTERRUPTED during a sweep, `s` while sweeping is ignored (single-sweep guard), navigation away stops further chunks. Pinned by Task 2.
5. **Confidence-threshold edges:** 0 and 1 are legal; out-of-range/blank/invalid → default 0.70 (get) or error (set); below-threshold suggestions NEVER prefill a modal and never unlock an implicit apply. Pinned by Task 1 kv tests + Task 3 gate tests + Task 4 settings tests.
6. **Concurrent mutation during sweep** (refreshAll mid-sweep from a sync): expected = chunk loop iterates the START-time id snapshot; merged suggestions for vanished notes are dropped live; activeIndex clamp law (P2) still holds. Pinned by Task 2.
